日期：2026-09-10
业务依据：Tiger_短视频获客_分阶段执行与防漂移总规范_V2.0.md
本次界面要求：老板轻量角色、Codex、剪辑师。取消旧多角色前台流转。

## 2. 从旧 TC-workflow 保留什么、取消什么

已读取 [TC-workflow](https://github.com/verayuan26/TC-workflow)，本次参考代码版本 `356f6bb059889ca9314ea54cee098364dbea3b02`。

| 旧实现 | 观察到的问题 / 可保留部分 | 本次处理 |
|---|---|---|
| React / Vite / TypeScript | 能承载现有任务界面 | 复用技术栈、依赖和锁文件 |
| 角色入口、RoleFlowPage | 小S、小M、小C、小A、Vera、PM等流转不适合当前三方模式 | 当前首页只保留三方视角，不再要求按角色接力 |
| taskStore.ts | 任务记录是模块内存；刷新不是可靠的生产恢复机制 | 不把它当生产真源；读取现有生产记录的快照 |
| workflowApi.ts | 另有一套模拟任务与发布数组 | 不将模拟数据和生产状态混用 |
| TaskPipelineTimeline / taskPipeline | 部分完成显示由状态序列及日志词推导 | 新阶段视图显式读取每阶段检验记录 |
| 剪辑任务详情 | 原有链接输入可以参考，但不等于文件已收齐 | 回传必须核对成片、工程、版本与文件完整性 |
| 老任务导入标准 | `plan_period.timezone=Asia/Shanghai`及旧字段已约定 | 保留；新快照是独立的界面读取协议，不偷偷改旧导入格式 |

原文件仍保留在代码仓库用于回查；新首页不暴露旧多角色界面。AGENTS.md未被覆盖。用户本轮明确的三方模式和工业视频业务要求优先于旧项目中相冲突的工作流默认值。

## 3. 只有三方，各自只承担一类工作

| 三方 | 首页看什么 | 做什么 | 不增加的负担 |
|---|---|---|---|
| 老板 | 完成、异常、询盘、下一步；真正需要决定的事项 | 首批集中确认样式；决定产品、市场、频率、预算或业务承诺的变化 | 不逐阶段审批，不审核机器编码项，不日常维护任务状态 |
| Codex | 当前真实阶段、未通过项、恢复入口、待接收回传 | 研究、素材匹配、脚本、配音、制作、检验、发布包、记录和复盘 | 不自建第二套任务真源，不改变固定业务范围 |
| 剪辑师 | 当前要处理哪一条、具体改哪里、素材在哪、怎么交、交给谁 | 核对画面与字幕、完成指定修订、交成片与实际工程、记录缺料 | 不写JSON、不跑命令、不管理数据库、不重复提交已确认模板 |

“负责人”与“状态”分别记录。老板不是每个阶段的最后一道门。技术检查通过的普通工作继续向前；确需人工的项目才出现在剪辑师待办。

## 4. 剪辑师每天怎么用

1. 打开“我的工作”，先看“待我处理”。没有任务就不需要手工追问九个阶段。
2. 打开具体任务，读“本次只需处理”。确认当前语言、内容类型和版本。
3. 点击“素材与预览”，播放完整预览，取得交接包。没有真实预览时不能把示例当成片。
4. 用现在习惯的剪辑工具修改。遵守原任务的主题、镜头事实、语言、声音和CTA。
5. 勾选这条内容适用的观感检查。机器负责尺寸、帧数、完整解码和音频测量。
6. 视频交修订MP4与实际工程或工程ZIP；图文交源文件与最终导出；短内容交最终正文及必要附件。
7. 写具体修改位置，例如“4–7秒字幕上移，保留工件边缘；未改旁白”。不要只写“已优化”。
8. 当前离线版：选择文件，下载自动生成的回传清单，将清单和原文件一起放入约定交接目录。剪辑师不编辑清单内容。正式接入后，这一步改成上传并提交，自动完成传输与回执。
9. 看到“待Codex接收与检验”后，转做下一条。只有生产端返回合格回执才可显示可交付。
10. 缺素材时写清“缺哪个镜头、现有替代是什么、哪条任务受影响”，通过问题单交给Codex。其他条目继续做。

老板只在首批合并看样或明确业务变化时进入决策页；不要恢复逐片审批。

## 5. 九阶段的人机落地与退出标准

| 阶段 | Codex负责 | 剪辑师负责 | 交付物 | 怎么检查、下一步 |
|---|---|---|---|---|
| S0 准备接入 | 核对真实状态，冻结合同，检查已有能力 | 提供已有素材位置、当前可用文件 | 配置、接入清单、恢复入口 | 同批重复启动不重复建任务；可用部分进入S1 |
| S1 选题验证 | 客户问题、关键词、能力匹配、SEO映射 | 核对画面可实现性，指出敏感或缺料部分 | 两个母题与依据 | 未知搜索量写未知；母题合格进入S2 |
| S2 素材任务 | 先查元数据，再匹配脚本；生成4视频+4配套任务 | 看清工件与动作，针对性补料 | 统一任务卡、镜头入出点、分轨与字幕 | 语言、CTA、来源、渠道一致；合格任务进入S3 |
| S3 首条制作 | 制作一条真实18秒成片并技术检查 | 有指定修订时处理观感 | 真实成片、分轨、报告 | 1080×1920 / 30fps / 540帧等按总规范；通过后继续，首条计入4条 |
| S4 恢复回传 | 恢复、幂等、半文件、旧版本、防覆盖检验 | 实际改一条并交回成片和工程 | 人工revision、说明、回执 | 至少一次真实人工闭环；待人工时继续其他预览 |
| S5 首周内容 | 补齐4母版与4配套，分类检查，合并看样 | 集中看俄英代表片和样式，处理异常 | 首周内容包、模板确认 | 通过后稳定模板仅抽检；就绪内容交S6 |
| S6 发布承接 | 展开固定日历，核对已有授权、入口、版本与远端结果 | 仅在实际需要人工发布时按包操作并交真实链接 | 发布包、平台链接、承接入口 | 就绪≠导出≠发布；失败只影响对应平台 |
| S7 周复盘 | 真实数据归因去重，生成下周同频计划 | 提供返工、耗时、镜头缺口 | 一屏周报、下周两个母题 | 无数据不是0；循环S2/S3/S5/S6，不重建底层 |
| S8 四周长片 | 同产品整合3–5分钟英文长片及复用包 | 组织图纸、实物、工程讲解，横片优先 | 1条长片、字幕、封面、章节 | 180–300秒，1920×1080，单独验收；下一周期 |

S0–S8是实施与生产阶段，不是所有任务必须排成一条串行长龙。S4有待人工项时，S5其他准备可以继续；页面保留各阶段独立状态和依据。

## 7. 给Codex的接入顺序：每一步交可验收成果

### 接入1：先把页面接到真实读取结果

动作：找到现有生产任务记录与SQLite。用只读适配器生成`workbench-snapshot.json`；复用本工作台，不再建另一套看板或数据库。若生产系统尚未实现，继续总规范的最早未完成阶段，只导出真实的未开始/缺项信息。

前端入口：`src/workbench/Workbench.tsx`。协议与检查：`src/workbench/domain.ts`。指南与演练：`src/workbench/data.ts`。

读取接口推荐：复用现有服务提供`GET /api/workbench/snapshot`；没有服务时先由生产端写原子快照文件，页面经受控本地服务读取。不要将SQLite直接放NAS共享写，也不要从公网浏览器连接本机路径冒充已接通。

测试：生产端改变一条任务，导出后页面只变化对应任务；刷新重新读取同一记录；断线显示最后更新时间与未同步；重复/过期快照被拒绝；演练文件不能进入实际模式。

通过条件：一次真实数据往返可复现，页面数字与生产记录一致。无数据仍显示未知，不填示例成果。

### 接入2：把人工文件回传跑通

动作：复用NAS或已有本地传输入口。提供领取、预览、下载、提问题、上传、提交六项能力；当前本地预览已提供操作原型，远端领取/上传/回执需要接入。工程大文件采用流式读写，不沿用网页演示的250MB单文件限制。

生产端必须按`content_id + base_revision + edit_generation`核对当前领取；按`request_id`去重；文件写临时路径，校验大小和SHA256后原子登记COMPLETE。未收齐只显示待接收，不标验收通过。禁止用文件名“final”判断最新版本。

人工结果新建revision，标记人工当前版本受保护。自动重跑仅生成候选，不覆盖。旧回传保留候选并给出过期原因，不能静默覆盖。

回执至少含：`request_id, content_id, accepted_revision, status, reason, qa_report_ref, updated_at`。状态区分`RECEIVING / RECEIVED / CHECKING / NEEDS_EDIT / ACCEPTED / STALE_REVISION`；不是新任务真源，回执由现有生产记录派生。

测试：一次真实领取→改片→成片与工程回传→技术检查→页面更新；断网半文件不消费；重复提交不重复revision；旧领取回传不覆盖；工程缺失保留成片并提示交接不完整，不影响其他任务。

通过条件：S4真实人工闭环有报告。剪辑师不用编辑JSON、运行命令或手动改阶段。当前网页生成的清单是一种过渡交换方式，不能当正式上传已完成。

### 接入3：批量、排程与轻量老板页

动作：首条计入首周4母版；补齐4配套。老板只接收一次合并代表片确认。集中审核记录保存在生产端，重复快照不重新创建审核。账号和已有发布授权接通后再执行排程。

测试：每周渠道数量正确；YT/IG用同一英文母版但有独立远端记录；图文不跑音频检查；缺一个账号只阻塞该平台；平台返回未知先核实不盲重发；排程后人工新版本使未发排程暂停或更新，已发布记录不被覆盖。

通过条件：生产状态、导出状态、发布状态分开；计划槽位不算完成；老板页合并异常和确需决定事项，不引入新增审批层。

### 接入4：恢复、周复盘与长片

动作：从真实记录生成不超过约60行的CONTINUE.md；恢复不重复付费或出片。按同产品积累长片素材，在第四周制作一条长片。定时采集或未来周期任务只有实际配置并验证后才称已启用。

测试：中断后从未完成项继续；旧进程晚到不覆盖；未知数据不写0；长片通过长片规则、短片仍严格按540帧检查；已发布历史与人工当前版本稳定。

通过条件：总规范相应测试通过并记录真实产物；不为了应用界面把所有S0–S8重新实施一遍。

## 8. 数据协议与防漂移

前台使用独立的只读工作台快照协议`tiger-workbench/1`，它不是旧AI任务导入JSON的替代品。旧导入格式仍保留原`status / review_reason / plan_period`等字段。生产端适配器负责映射。

| 对象 | 必需信息 | 约束 |
|---|---|---|
| 快照 | source、schema_version、spec_version、cycle_id、source_revision、generated_at | 明确production/demo；版本递增；导入不等于联网核验 |
| 阶段 | id、status、evidence | S0–S8独立记录；PASSED须有报告引用；前台无强行通过按钮 |
| 内容任务 | id、kind、language、week、revision、edit_generation、owner、next_action、input_refs | 同母题双语同义；ID与渠道映射固定；只有三方负责人 |
| 技术通过 | qa.revision、qa.status、qa.report_ref | TECH_PASSED/READY必须对应当前版本报告；生产端实际核对文件与检验结果 |
| 发布 | slot id、content_id、revision、date、time、timezone、status、published_url | 41个固定槽位；已设定时引用当前READY版本；已发保留当时revision和链接 |
| 人工回传 | content_id、base_revision、edit_generation、request_id、files、checks、note | files含大小、SHA256；重复请求不重复入库；前台只显示待回执 |
| 指标 | inquiries、qualified | 未知为null；数据真实性与去重由生产端核验 |

当前协议仅针对CYCLE01和V2.0固定规则。下一周期由Codex依据明确的周期配置版本化扩展，不通过任意删掉检查或放宽字段来绕过规则。

前端校验只挡住明显格式/范围错误，不证明报告内容真实。生产端必须读报告、核对产物指纹、实际QA与权限。不要以“JSON导入成功”宣布生产验收成功。

正式多人使用前，将演练视角切换替换为受控身份与真实领取操作；服务端校验权限和领取版本。无需添加PM或新增审核者，仍只有三方。

## 9. 本次检查与交付边界

已执行：TypeScript检查、新增前端文件静态检查、构建，以及13组关键约束测试，包括数量与复用、时区、演练隔离、缺报告不通过、语言/时间漂移、过期快照、发布链接与版本、历史保护、回传工程与请求去重、内容类型区别。

未执行：真实素材生产、NAS传输、实际人工回传、平台上传、外部发布或询盘回收。网页的文件SHA256只核对所选本地字节，不等于媒体解码已通过。未进行浏览器端视觉或端到端验收。
